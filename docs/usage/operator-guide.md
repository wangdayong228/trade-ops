# 操作员使用说明

本手册说明如何在本机界面完成「开空合约，同时买现货」。行为以当前代码为准；平空并卖出现货尚未实现。对冲任务 ID 是一次开仓作业的编号，不是单笔交易所订单。

入口：`http://127.0.0.1:3000/`（默认 `HOST`/`PORT`）。服务只绑定回环地址，不要用反向代理暴露到局域网或公网。

## 启动前检查

1. 已安装 Node.js 20+，并完成 `npm install`、配置 `.env`、`npm run build`、`npm start`（详见 [README](../../README.md)）。
2. Bitget 与 OKX 均已配置 USDT 现货与 USDT 线性永续；合约为双向持仓（hedged）。服务不会自动改账户模式或杠杆。
3. API key 具备读取与交易权限，且已关闭提现。
4. 同一数据库只允许单进程运行。
5. OKX 若当前无合约数量为正的空头仓位，预检可能因保证金模式/杠杆无法唯一确认而拒绝；零合约占位行仍视为空仓。

## 页面结构

界面从上到下四块：

| 区块 | 用途 |
| --- | --- |
| 开仓参数 | 填写交易所、交易对、数量、执行模式，点「预检」 |
| 加载已有对冲任务 | 用对冲任务 ID 恢复查看；待确认任务可继续确认 |
| 预检快照 | 核对余额与账户设置，勾选风险后「确认开仓」/「刷新状态」 |
| 执行状态 | 对冲任务 ID、状态、实际成交与订单 ID |

页面顶部提示语：先预检，再由操作员明确确认；受理不代表执行成功，请持续刷新状态。

## 新开一笔对冲

### 1. 填写开仓参数

| 字段 | 说明 |
| --- | --- |
| 现货交易所 | 从下拉选择；页面加载时从 `GET /api/exchanges` 填充，本期为 `bitget` / `okx` |
| 合约交易所 | 同上；必须与现货交易所不同 |
| 交易对 | 默认 `BTC/USDT`；格式需符合界面校验（基础币 + `/USDT`） |
| 基础资产数量 | 目标基础币数量（正数）；实际可成交量以预检「有效数量」为准 |
| 执行模式 | 见下文「三种执行模式」 |

任一项开仓参数变更后，界面会清空可操作预览，并提示重新预检。

### 2. 预检

点击「预检」。成功时 HTTP `201`，对冲任务进入 `PENDING_CONFIRMATION`，并生成对冲任务 ID。

请立即在「执行状态」中**抄写并保存对冲任务 ID**（UUID）。服务重启后靠它加载。

每次预检依次刷新现货和合约市场，再检查账户设置、共同数量、两腿名义金额与资金。首次失败立即停止，不会创建对冲任务。消息区显示对象、期望和实际等详细错误（见「界面错误与日志」）；常见原因包括账户非双向持仓、设置无法确认、余额不足、市场规则或精度不满足。

### 3. 核对预检快照

| 字段 | 含义 |
| --- | --- |
| 输入数量 | 你填写的请求数量 |
| 有效数量 | 预检后共同可交易基础币数量（不会大于输入数量）；模式与后续下单以此为目标，忽略手续费 |
| 现货/合约参考价 | 预检时参考价 |
| 现货/合约 USDT 余额 | 可用 USDT |
| 保证金模式 | `isolated` 或 `cross`（不可由本服务修改） |
| 持仓模式 | 必须为 `hedged` |
| 杠杆 | 预检确认的空头杠杆 |

### 4. 确认开仓

1. 勾选：「我理解顺序模式和差额补单可能长期产生单边敞口」。
2. 点击「确认开仓」（须已预检成功、已勾选、且无进行中的请求）。
3. 等待同步复检：服务重新刷新市场并检查账户、数量和资金；市场身份、规则、有效数量及账户设置须与预检快照一致，价格和余额可变化但必须仍满足要求。复检与执行认领事务提交成功后返回 HTTP `202`，界面提示「确认已受理，正在后台执行」；此时任务进入 `EXECUTING`，**不是**对冲完成。
4. 反复点击「刷新状态」，观察对冲状态与成交量，直到终态或需要人工介入。

确认按钮在以下情况保持禁用：未预检、未勾选风险、请求进行中，或对冲任务已不在可确认状态。

复检失败且失效记录提交成功时，确认返回 `409` 并保留具体原因，任务进入 `PREFLIGHT_INVALIDATED`，不会创建订单。修正原因后，重新填写或核对参数并点击「预检」，使用新任务 ID 确认。操作锁忙同样返回 `409`，错误码为 `STRATEGY_OPERATION_BUSY`；它不表示任务已失效，刷新状态后按实际状态操作。

存储失败返回 `500`，不会受理执行。若错误说明事务结果无法确认，该仓储实例会停止后续策略读写与恢复；先检查安全错误和数据库运行条件，再正常停止并重启服务，让数据库重新验证，不能把这次请求当作已成功确认。

### 5. 阅读执行状态

| 字段 | 含义 |
| --- | --- |
| 对冲任务 ID | 本次对冲任务的唯一 ID |
| 对冲状态 | 见「对冲状态与操作员动作」 |
| 现货实际成交 | 本任务现货买单累计成交基础币数量 |
| 合约做空实际成交 | 本任务合约空头累计成交基础币数量 |
| 未匹配基础资产数量 | 两侧实际成交量之差的绝对值 |
| 现货/合约订单 ID | 展示 `exchangeOrderId` 与 `client` 订单 ID；尚未分配交易所 ID 时显示「待交易所分配」 |

## 三种执行模式

三种模式都以预检「有效数量」为目标，忽略交易手续费。

### `CONTRACT_FIRST`（合约优先）

1. 先提交合约市价开空。
2. 取得该单实际正成交量与实际平均成交价后，再按该成交量在现货侧挂买入 GTC 限价单；限价取第一腿实际均价，并按现货交易所规则量化。
3. 若市价单首次仍为 `open`/`unknown`，监控器确认可靠终态后由同一协调器继续第二腿。

### `SPOT_FIRST`（现货优先）

与上对称：先现货市价买，再按实际成交量在合约侧挂开空 GTC。

### `CONCURRENT`（并发）

1. 同时提交现货市价买与合约市价开空（进程内并发，非交易所原子成交）。
2. 两侧实际正成交量相等则完成（无需均价）。
3. 不相等时，在成交量较小一侧挂一张 GTC，数量等于差额，价格取较大一侧实际均价并按较小侧规则量化。
4. 一侧可靠终态零成交时同样在零成交侧挂差额；两侧均可靠终态零成交则失败。

共通规则（操作员需知）：

- 只用本任务订单的**实际成交量**，不用委托量代替。
- 市价单仍为 `open`（含零成交或部分成交）时保持 `EXECUTING` 并继续查同一订单；可靠终态后才算敞口或建 GTC。
- 市价单以 `canceled` 终态返回但已有可靠正成交时，成交仍有效。
- GTC 可能长期未完全成交；本期**不会**自动撤单、改价、重提、回滚、平仓或追单。

## 对冲状态与操作员动作

| 状态 | 含义 | 你该做什么 |
| --- | --- | --- |
| `PENDING_CONFIRMATION` | 预检成功，等待确认 | 核对快照，勾选风险，点「确认开仓」 |
| `PREFLIGHT_INVALIDATED` | 确认复检失败，无订单；终态 | 查看精确错误、修正原因并重新预检；旧任务不能再次确认 |
| `EXECUTING` | 正在提交/查询市价单或恢复中 | 刷新状态；监控器可能自动继续第二腿；不要重复改参数开新预检除非你有意新开 |
| `WAITING_HEDGE` | 已有 GTC，等待对冲成交 | 「确认开仓」保持不可用；刷新状态；在两家交易所关注真实订单 |
| `HEDGED` | 对冲完成 | 仅可加载查看，不能再次确认 |
| `HEDGE_INCOMPLETE` | 对冲不完整或需人工处理 | 见下一节；不能再次确认 |
| `FAILED` | 失败（通常无有效正成交敞口） | 记录失败信息与订单；不能再次确认 |

`FAILED` / `HEDGE_INCOMPLETE` 带 `failureCode`（如 `ORDER_SUBMISSION_FAILED`、`NO_FILL`、`HEDGE_ORDER_CANCELED`）。`PREFLIGHT_INVALIDATED` 使用独立的 `preflightFailure` 完整错误详情；它没有订单，也不表示执行阶段失败。结合 stdout 中的交易事件与请求 ID 诊断。

## 重启后加载已有对冲任务

监控器启动后会立即读取同一 SQLite。操作步骤：

1. 打开界面，在「加载已有对冲任务」填入原对冲任务 ID（UUID v4），点「加载任务」。
2. 加载成功会回填开仓参数并渲染状态；风险勾选会被清空。
3. 只有 `PENDING_CONFIRMATION` 可重新勾选风险并确认，确认时仍会完整复检。
4. 若为 `EXECUTING` / `WAITING_HEDGE`，由监控器自动恢复，操作员只需刷新；确认按钮不可用，再次确认返回 `409`。
5. 若为 `PREFLIGHT_INVALIDATED`，加载后仍能查看原失败详情；修正原因并重新预检。`HEDGED` / `HEDGE_INCOMPLETE` / `FAILED` 也仅供查看。

加载框中的对冲任务 ID 变更会清空当前可操作预览，需重新加载。

服务启动时将受支持的策略 schema v1/v2 自动迁移至 v3，保留已有订单、提交证据、事件及资金费率数据。升级前停止服务并进行一致的离线备份；未知或损坏的 schema 会阻止启动，不会跳过校验继续恢复。备份与单进程数据库要求见 [README](../../README.md#环境变量)。

## `HEDGE_INCOMPLETE` 时的人工处理

本期不提供自动修复、自动回滚或自动平仓。

1. 在界面记录两家交易所、所有 client order ID 与 exchange order ID。
2. 分别登录 Bitget 与 OKX，核对订单状态、实际成交量、方向，以及现货余额与合约空头仓位。
3. 对照界面的现货实际成交、合约做空实际成交与未匹配数量。
4. 在本服务之外人工决定补单、撤单或调整仓位。

GTC 一旦计划或提交，系统只观察该确定性 client order ID，绝不自动创建替代单。交易所侧撤单或拒单可使对冲任务进入 `HEDGE_INCOMPLETE`。

## 界面错误与日志

交易所列表加载、预检、任务加载、状态刷新、确认失败时，消息区会显示：

- HTTP 状态与稳定错误码；
- 中文说明、阶段、对象、期望和实际；
- 请求 ID（用于对照 stdout）。

例如，确认复检发现 OKX 已不是双向持仓时，失效事务提交成功后返回 HTTP `409`：

```json
{
  "requestId": "req-1",
  "error": {
    "code": "ACCOUNT_POSITION_MODE_MISMATCH",
    "phase": "confirmation",
    "subject": {
      "type": "account",
      "exchangeId": "okx",
      "symbol": "BTC/USDT",
      "field": "positionMode"
    },
    "expected": "hedged",
    "actual": "one-way",
    "message": "账户持仓模式检查失败（交易所 \"okx\"、账户市场 \"BTC/USDT\"、字段 \"positionMode\"）：期望 字符串 \"hedged\"，实际为 字符串 \"one-way\"",
    "occurredAt": "2026-10-02T08:00:00.000Z"
  }
}
```

错误体只有 `requestId` 与 `error` 两个顶层字段。`400` 表示请求格式错误，`403` 表示 Host/Origin 被拒绝，`404` 表示策略或路由不存在，`409` 表示确认锁忙、状态不允许或复检已失效，`422` 表示首次业务预检未通过，`500` 表示安全转换后的内部或存储失败。应结合具体错误码和详情判断，不能只凭状态码认为任务已失效。

stdout 中，每个完成的 HTTP 请求只记录一条 `request completed`。状态码低于 `400` 时级别为 `info`，且不带失败请求快照；`4xx` 为 `warn`，`5xx` 为 `error`。失败日志包含 `httpError` 和 `httpRequest`；后者只包含 `method`、含 query 的 `url`、`body`、`truncated`、`originalByteLength`。Host/Origin 在任何 body 观察或 parser 之前检查；该边界早拒绝的 `403` 不读取或缓存攻击 payload，日志 body 为 `null`。路由解析前发现畸形 URL 时返回结构化 `400`，保留安全响应头与一条完成日志，不读取 body，日志 URL 使用 `[Unavailable]`。

全局 Fastify body 解析上限显式为 `1 MiB`，原始 body 观察另有固定 `1 MiB` 安全预算；路由显式配置更大的解析上限也不会扩大观察预算。无法安全结构化的原始正文（例如畸形 JSON）一律记录为 `[Unavailable]`，不输出原文或前缀。解析后的 body 会递归隐藏 API key、secret、password、passphrase、signature、authorization、cookie 等凭证字段，以及 credentials/auth 容器；query 中对应的字段也会在解码键名后隐藏，普通诊断字段保留。当前已配置的敏感值仍先被完整替换，再将最终 body 按 UTF-8 最多 `8192` 字节截断；`1 MiB` 是原始观察安全预算，`8192` 是最终日志输出上限。任何请求 headers 和响应 body 都不记录，也不记录原始 CCXT 请求/响应、完整环境变量或任意错误属性。启动与 HTTP 错误只保留受控安全详情，不透传第三方消息、cause 链或 stack；凭证错误实际值仅为 `missing` 或 `present-but-invalid`。

预检失败不会向 SQLite 写入对冲任务。同步请求失败不会再另写 `unhandled_http_request_failure`。确认返回 `202` 后，该 HTTP 请求的完成日志已经结束；之后的后台执行属于独立边界，异步失败仍记录 `background_confirmation_failed`，应结合界面持久化状态、失败码与订单生命周期事件诊断。

stdout 为逐行 Pino JSON。与订单生命周期相关的事件名包括：`order_planned`、`order_submit_started`、`order_submit_succeeded`、`order_submit_uncertain`、`order_rejected_before_submit`、`order_status_changed`、`order_terminal`。

## 界面不可用时的诊断备选

优先使用本界面。必要时：

- `GET /api/hedges/:id` 查看对冲任务与订单快照；
- `POST /api/hedges/:id/confirm` 必须精确 JSON `{ "riskAcknowledged": true }`，且 `Origin` 须与原始回环 `Host`（含端口）完全匹配。这不是绕过风险确认的后门。

## 范围外

- 卖出现货并平掉合约空单：未实现（见 [功能清单](../manual/feature_list.md)，非规范）。
- 自动改账户模式、杠杆、自动追单/回滚/平仓：不会做。
- 真实资金与交易所联调：自动化测试使用 fake 网关；接入真实账户前由操作员独立核对账户与风险（见 [README](../../README.md)）。
