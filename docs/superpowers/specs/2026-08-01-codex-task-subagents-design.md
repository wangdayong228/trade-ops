# Codex 任务子代理体系设计

## 1. 背景

`trade-ops` 是涉及真实资金、交易所外部语义、订单幂等、恢复拓扑、数量精度和账户权限的高风险项目。复杂任务需要并行探索、实现、测试和审查，但不能让多个代理无边界地同时修改代码，也不能把现有 brainstorming、TDD 和完成验证流程复制到每个子代理中。

Codex 当前支持项目级自定义 agent：每个角色由 `.codex/agents/` 下的独立 TOML 文件定义，项目默认值位于 `.codex/config.toml`。自定义 agent 未固定 `model` 和 `model_reasoning_effort` 时，主代理可以在委派时根据任务风险显式选择模型；未显式选择时使用 `[agents]` 默认值。

## 2. 目标

- 为项目提供覆盖调查、外部语义核实、测试设计、实现、风险审查和验证的子代理体系。
- 由主代理根据代码复杂度和资金/安全风险动态分配模型。
- 普通任务也只使用 `high` 推理级别，不使用 `medium` 或 `low`。
- 低成本完成探索和常规任务，在资金关键路径上升级模型和推理强度。
- 允许安全的只读工作并行执行，同时保证源码或测试最多只有一个写入者。
- 子代理只负责窄职责；主代理继续负责需求、流程门禁、结果裁决和最终结论。
- 所有自动化验证与真实凭证、真实账户、真实交易所和真实订单严格隔离。

## 3. 非目标

- 不创建新的总控编排 Skill。
- 不在子代理中重新实现 brainstorming、writing-plans、TDD 或 verification 技能。
- 不让子代理自行继续委派其他子代理。
- 不允许多个写入型子代理并行修改源码或测试。
- 不允许代理使用真实 `.env`、真实交易凭证或真实交易所账户。
- 不引入新的 MCP 服务、远程执行服务或外部代理平台。
- 不让任何子代理独立宣称整个任务已经完成。

## 4. 产出结构

新增以下项目级配置：

- `AGENTS.md`
  - 定义主代理编排规则、动态模型路由、单写入者约束和交易安全边界。
  - 引用现有技能作为流程的唯一来源，不复制技能内容。
- `.codex/config.toml`
  - 启用多代理。
  - 设置默认子代理模型和推理级别。
  - 限制每个会话的最大并发子代理数。
- `.codex/agents/context-explorer.toml`
- `.codex/agents/source-verifier.toml`
- `.codex/agents/test-designer.toml`
- `.codex/agents/implementer.toml`
- `.codex/agents/risk-reviewer.toml`
- `.codex/agents/verifier.toml`

各 agent 文件定义 `name`、`description`、`developer_instructions` 和适用的 sandbox。它们不固定 `model` 或 `model_reasoning_effort`，避免覆盖主代理在委派时做出的动态选择。

## 5. 主代理职责

主代理始终负责：

1. 与用户澄清需求和成功标准。
2. 按现有规则调用 brainstorming、writing-plans、TDD、systematic-debugging 和完成验证技能。
3. 判断是否需要子代理，以及需要哪些角色。
4. 在每次委派前评估复杂度与资金/安全风险。
5. 提供完整、结构化且有边界的子代理上下文。
6. 控制并行关系，保证同一时刻最多一个源码或测试写入者。
7. 检查子代理返回的代码、证据和命令结果，而不是直接接受其结论。
8. 裁决冲突、安排修复和重新验证。
9. 只有在既有完成验证技能链结束后，才能给出整个任务的完成结论。

## 6. 动态模型路由

### 6.1 默认配置

`.codex/config.toml` 使用以下默认值：

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 4
default_subagent_model = "gpt-5.6-terra"
default_subagent_reasoning_effort = "high"
```

不允许为任何任务选择 `medium` 或 `low`。

### 6.2 委派前评估

主代理必须在委派上下文中写明：

- 复杂度：普通或高；
- 资金/安全风险：无影响、间接影响或直接影响；
- 选择的模型与推理级别；
- 一句可核查的选择理由。

风险等级优先于代码复杂度。无法确定风险时按直接影响处理。

### 6.3 路由规则

- 普通复杂度且不涉及资金或安全：
  - `gpt-5.6-terra + high`
- 高复杂度，或间接涉及资金/安全：
  - `gpt-5.6 + high`
- 直接涉及资金、安全、权限或不可逆外部副作用：
  - `gpt-5.6 + xhigh`

直接影响包括但不限于：

- 下单、订单查询、撤单或恢复；
- client order ID、角色唯一性和重复提交防护；
- 策略状态机、恢复拓扑和故障分类；
- 数量、价格、精度、舍入、单位和成交计算；
- SQLite 事务、持久化顺序和并发所有权；
- 账户模式、杠杆、权限、凭证和认证材料；
- Bitget、OKX 或 CCXT 的外部接口语义；
- 可能触发真实资金变化的任何代码路径。

如果当前 Codex 客户端或所选模型不支持 `xhigh`，不得静默降到 `medium` 或 `low`。主代理最多使用 `high` 作为明确披露的降级，并把能力差异列为验证限制。

## 7. 子代理定义

### 7.1 `context_explorer`

- Sandbox：`read-only`
- 职责：
  - 定位入口、调用链、状态转换、测试和受影响路径；
  - 查明现有约束和仓库惯例；
  - 返回文件、符号和证据。
- 禁止：
  - 修改文件；
  - 在没有证据时猜测行为；
  - 主动提出或实施修复，除非主代理明确要求分析候选方案。

### 7.2 `source_verifier`

- Sandbox：`read-only`
- 职责：
  - 核实 CCXT、Bitget、OKX 和其他外部接口的字段语义；
  - 核对单位、精度、舍入、状态和错误行为；
  - 优先使用官方文档、依赖源码和仓库内已有资料；
  - 返回来源、适用版本、确定结论和未解决歧义。
- 禁止：
  - 调用任何真实交易所 API，包括公共市场数据和账户接口；
  - 读取真实凭证；
  - 把字段名称或注释当作未经验证的事实；
  - 修改项目文件。

### 7.3 `test_designer`

- Sandbox：`workspace-write`
- 职责：
  - 从批准的 spec、plan 和风险面构建测试矩阵；
  - 先编写能证明业务规则的失败测试；
  - 运行聚焦测试并确认其因预期原因失败；
  - 返回测试文件、风险覆盖和红灯证据。
- 禁止：
  - 修改生产实现；
  - 削弱现有断言；
  - 使用真实交易所、真实凭证或持久业务数据库；
  - 在尚无批准计划时自行扩大测试范围。

### 7.4 `implementer`

- Sandbox：`workspace-write`
- 职责：
  - 只按批准的 spec、plan 和失败测试实施最小完整改动；
  - 遵循现有代码边界、类型和错误处理方式；
  - 保持测试语义，不以修改断言来迁就实现；
  - 返回修改文件、实现摘要、已运行命令和剩余不确定项。
- 禁止：
  - 修改无关文件；
  - 提交、推送或改写 Git 历史；
  - 自行引入未批准的依赖、抽象或业务规则；
  - 启动使用真实 `.env` 的服务或访问真实交易所。

### 7.5 `risk_reviewer`

- Sandbox：`read-only`
- 职责：
  - 以缺陷优先方式审查资金安全和行为回归；
  - 检查订单幂等、恢复拓扑、状态机、事务边界、精度、权限和失败安全；
  - 检查受影响路径和测试缺口，不只查看直接 diff；
  - 返回按严重度排序、可定位且可操作的发现。
- 禁止：
  - 修改文件；
  - 报告没有行为影响的纯风格意见；
  - 在证据不足时把猜测表述为缺陷；
  - 宣称整个任务已经通过审查。

### 7.6 `verifier`

- Sandbox：`workspace-write`
- 职责：
  - 执行批准计划中的聚焦测试、完整测试、构建和安全进程级验证；
  - 核对 spec、plan、代码、测试、README 和配置的一致性；
  - 返回命令、退出状态、关键输出和未执行项。
- 写入权限仅用于构建、测试和临时验证产物，不得编辑源码或测试。
- 禁止：
  - 使用真实 `.env`、真实数据库或真实交易所；
  - 为使验证通过而修改文件；
  - 把单个命令成功扩展为整个任务完成。

## 8. 编排流程

### 8.1 调查和设计

主代理执行现有 brainstorming 流程。需要仓库证据时调用 `context_explorer`；需要外部接口语义时调用 `source_verifier`。两者互不写入，可以并行执行。

子代理只为设计提供证据。书面 spec、用户批准和 writing-plans 门禁仍由主代理及现有技能负责。

### 8.2 测试和实现

批准计划存在后：

1. 主代理调用 `test_designer`。
2. 主代理检查测试矩阵和预期红灯证据。
3. 测试因预期原因失败后，主代理调用 `implementer`。
4. `implementer` 不得与 `test_designer` 同时写入。

纯文档或无行为影响的机械修改可以跳过 `test_designer`，但必须由主代理明确说明不需要失败测试的原因。

### 8.3 审查和验证

实现完成后，`risk_reviewer` 和 `verifier` 可以并行工作，因为前者只读，后者只执行验证命令。

发现问题时：

1. 主代理核实发现是否成立。
2. 成立的问题交回 `implementer` 串行修复。
3. 修复后重新运行受影响验证。
4. 高风险变更必须重新经过 `risk_reviewer`。

### 8.4 按需调用

主代理不应机械地为每个任务启动全部六个角色：

- 只读解释：通常只需 `context_explorer`。
- 外部 API 语义调查：使用 `source_verifier`，必要时配合 `context_explorer`。
- 普通行为修改：使用 `test_designer`、`implementer` 和 `verifier`。
- 资金关键修改：使用全部相关角色，并保证至少一次 `gpt-5.6 + xhigh` 的独立风险审查。
- 纯文档或机械修改：可以只使用 `implementer` 和必要验证。

## 9. 委派上下文契约

每次委派必须包含：

```text
Goal: 用户目标与可验证的完成标准
Scope: 允许修改路径和禁止修改路径
ApprovedArtifacts: 已批准的 spec 与 plan
Risk: 复杂度、资金/安全等级、模型选择及理由
RelevantFiles: 关键文件、符号和必要事实
Constraints: 代码风格、最小改动、流程与安全限制
Tests: 允许和要求执行的测试命令
DoNot: 不提交、不推送、不触达真实凭证/账户/交易所、不改无关文件、不继续委派
Return: 证据、发现或改动摘要、文件列表、命令结果、未执行项和不确定项
```

缺少批准产物时，写入型子代理必须停止并向主代理报告；只读调查不受此限制。

## 10. 安全边界

所有角色共同遵守：

- 不读取、打印、复制或推断真实凭证。
- 不使用项目真实 `.env` 启动服务。
- 不调用 Bitget、OKX 或其他真实交易所 API，包括公共市场数据和账户接口。
- 不提交订单、撤销订单、修改账户模式或改变杠杆。
- 不使用真实业务 SQLite；测试使用 fake gateway 和临时或内存数据库。
- 允许访问公开官方文档，但不得把公开文档访问扩大为账户 API 请求。
- 允许执行 `npm test`、`npm run build`、聚焦测试以及使用临时环境和安全失败前置条件的进程级验证。
- 任何可能越过这些边界的命令都必须停止，而不是请求子代理自行放宽权限。

## 11. 失败与冲突处理

- 子代理超时、失败或证据不足时，主代理缩小范围后最多重试一次。
- 第二次仍失败时，主代理明确报告未完成项和影响，不得静默跳过。
- 子代理意见冲突时，主代理以代码执行路径、可复现测试和权威来源裁决。
- 不得用多数意见替代证据。
- 写入代理留下超出范围的改动时，主代理停止后续阶段并先处理范围污染。
- 验证工具缺失或模型不支持目标推理级别时，明确报告限制，不得虚构执行或能力。
- 任何角色都只能报告其局部结果；最终完成结论只能由主代理给出。

## 12. 验证策略

实现配置后执行以下验证：

1. 检查所有 TOML 文件语法和必填字段。
2. 确认 `.codex/config.toml` 默认模型为 `gpt-5.6-terra`、默认推理为 `high`、最大并发为 4。
3. 确认六个 agent 文件均未固定模型或推理级别。
4. 确认只读角色使用 `read-only` sandbox。
5. 确认 `test_designer`、`implementer` 和 `verifier` 的写入权限及各自禁写边界清楚。
6. 使用当前 Codex 客户端检查项目配置和六个角色能否被加载。
7. 使用代表性提示验证路由：
   - 代码路径探索使用 `gpt-5.6-terra + high`；
   - 普通复杂度修改使用 `gpt-5.6-terra + high`；
   - 跨模块高复杂度任务升级到 `gpt-5.6 + high`；
   - 下单、精度或恢复改动升级到 `gpt-5.6 + xhigh`。
8. 验证只读角色不能修改文件。
9. 验证写入角色不会并行修改源码或测试。
10. 检查 `AGENTS.md` 只引用既有技能流程，不复制或改变其门禁。

任何依赖实际模型权限或 Codex UI 的加载测试，如果无法在自动化环境中完成，必须列为人工验证项，不得声称已经通过。

## 13. 完成标准

- 项目包含一个简洁的 `AGENTS.md`、一个 `.codex/config.toml` 和六个职责清晰的自定义 agent 文件。
- Codex 能识别六个角色，或明确记录因当前客户端/权限导致的人工验证项。
- 默认模型是 `gpt-5.6-terra + high`，不存在 `medium` 或 `low` 配置。
- 高复杂度和资金/安全任务按照规则升级到 `gpt-5.6 + high/xhigh`。
- 主代理保留需求、门禁、模型路由、冲突裁决和最终结论责任。
- 子代理之间没有流程职责重叠，也不会重复既有 brainstorming 和 verification 技能。
- 源码或测试始终只有一个写入者；只读调查和审查可以并行。
- 所有测试和验证与真实凭证、真实账户、真实交易所和真实订单隔离。
