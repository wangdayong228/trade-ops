# 跨交易所现货—永续合约等量对冲开仓设计

日期：2026-07-26

状态：已批准

## 1. 目标

为资金费率套利提供人工触发的跨交易所开仓能力。用户指定现货交易所、合约交易所、交易标的、标的币数量和执行模式；系统买入现货并开立等量的 USDT 本位永续合约空仓。

本策略以最终形成等量的标的币多空持仓为目标。系统不会因为第二腿未成交而回滚第一腿；未成交的 GTC 限价单持续保留和监控。

## 2. 范围

### 2.1 本期包含

- 人工触发开仓。
- 用户分别指定现货交易所和合约交易所；第一版仅支持 Bitget 与 OKX，二者的现货和合约角色可以互换。
- 用户按标的币数量输入开仓规模，例如 `1 BTC`。
- 支持“并发”“合约优先”“现货优先”三种显式执行模式。
- 支持市价成交后的 GTC 等量补单。
- 持久化策略和订单状态，服务重启后恢复监控。
- 展示并沿用合约账户当前的保证金模式、持仓模式和杠杆设置；本期只允许双向持仓（hedged/long-short）模式。

### 2.2 本期不包含

- 自动筛选交易所、交易对或资金费率机会。
- 根据手续费调整第二腿限价。
- 自动撤单、改价、重复下单、回滚或平仓。
- 修改合约账户的保证金模式、持仓模式或杠杆设置。
- 卖出现货并平掉合约空单。该能力在功能清单中标为后续事项。
- 币本位合约、交割合约和非 USDT 计价交易对。
- Bitget 与 OKX 以外的交易所。

## 3. 核心定义与不变量

### 3.1 等量对冲

“等量”指本策略产生的现货实际买入标的数量与永续合约实际做空标的数量相等，而不是订单张数相等。合约张数必须根据合约乘数换算为标的币数量。

系统只统计本策略订单产生的增量成交，不把账户中原有的现货余额或合约持仓计入本策略的完成度。

### 3.2 等价限价

顺序模式的第二腿限价等于第一腿实际成交均价；并发模式的差额限价等于成交数量较多一腿的实际成交均价。不计算手续费。

若交易所统一订单未返回平均成交价，或返回语法有效但不可靠的零值哨兵，系统只在单位匹配时按订单的正 `cost / filled` 计算；否则仅在成交明细完整且交易所、订单、市场、方向身份一致时，按精确十进制成交成本加权计算。缺少可靠数据时不猜测均价；负数或非数字统一均价仍按畸形响应拒绝。价格按第二家交易所的价格精度取最接近的有效价格，因此最终有效限价可能与第一腿均价存在一个最小价格单位以内的差异。

Bitget 现货市价买单由适配器在提交前读取最新卖价（缺失时使用最新成交价）并换算为报价币金额，以满足 Bitget 的市价买入语义。该价格只用于换算提交金额，绝不作为实际成交均价；策略始终以订单实际买到的标的币数量作为对冲目标。无法取得可靠参考价格时阻断下单。

### 3.3 长期等待

“长期等待”指使用不设置本地到期时间的 GTC 限价单，并持续监控该订单。它不代表跨交易所原子成交，也不保证交易所永远不取消订单。

系统不主动撤销、改价或重下 GTC 订单。若订单被交易所或外部操作取消，策略进入“对冲未完成”状态。

## 4. 技术选型

- 语言：TypeScript，开启严格类型检查。
- 运行时：Node.js 24 LTS。
- 交易所接口：CCXT。
- 持久化：SQLite，第一版采用单进程部署。
- 金额计算：使用十进制定点数库；禁止使用 JavaScript 原生浮点数直接计算订单价格、数量、合约乘数或成交差额。

选择 TypeScript 是因为 CCXT 的源实现和类型定义以 TypeScript 为基础，同时该策略需要清晰约束订单方向、市场类型、标的数量、合约张数和状态转换。SQLite 足以支持第一版的事务、唯一约束和重启恢复，不引入独立数据库服务。

## 5. 用户输入与确认

用户必须提供：

- 现货交易所。
- 合约交易所。
- 交易标的，例如 `BTC/USDT`。
- 标的币数量，例如 `1 BTC`。
- 执行模式：并发、合约优先或现货优先。

执行模式必须在界面中显式显示和选择，不提供隐式默认切换。

下单确认界面至少展示：

- 两家交易所及对应市场。
- 用户输入数量与规范化后的实际执行数量。
- 执行模式及对应下单顺序。
- 合约账户当前保证金模式、持仓模式和杠杆。
- 双向持仓模式要求；单向持仓预检不可执行且不会持久化策略或提交订单。
- 当前余额与可用保证金检查结果。
- 顺序模式或并发差额补单可能长期产生单边敞口的风险提示。

用户确认后才创建可执行策略并提交订单。

## 6. 下单前校验

系统在确认和下单前检查：

1. 两家交易所连接正常，API 凭证具备所需的读取和交易权限。
2. 现货市场和 USDT 本位永续市场存在、可交易，并具有相同标的币和 `USDT` 计价币。
3. 现货账户可用 USDT 和合约账户可用保证金满足下单前估算。
4. 输入数量满足两边的最小下单量、最大下单量、数量精度和合约乘数要求。
5. 合约账户的保证金模式和杠杆可以读取，持仓模式必须是双向持仓；单向或未知模式预检失败，系统不自动修改账户设置。

余额和保证金校验是下单前快照，不保证下单时市场价格和账户余额不发生变化。

### 6.1 共同可执行数量

系统分别按现货数量步长和合约乘数计算可执行的标的币数量，并向下调整为两边都能准确表达的最大共同数量。

如果共同数量小于任一市场的最小下单量，预检失败。如果共同数量小于用户输入数量，确认界面必须同时展示原始数量和实际执行数量。

## 7. 执行流程

### 7.1 合约优先

1. 合约侧按实际执行数量提交市价开空单。
2. 等待该市价单达到可靠终态并读取实际成交数量 `Q` 与成交均价 `P`；`open`（含零成交或部分成交）期间保持 `EXECUTING`，不创建第二腿。
3. 如果 `Q` 为零，不提交现货订单，策略进入“执行失败”。
4. 如果 `Q` 大于零，现货侧提交数量 `Q`、限价 `P` 的 GTC 买单。
5. GTC 单部分成交时继续保留剩余数量，直至完全成交或发生外部取消、交易所取消或拒单。

若第一腿市价单在 `closed` 或 `canceled` 终态只部分成交，以可靠的实际成交数量 `Q` 作为最终对冲目标，不继续追求用户最初输入的数量。

### 7.2 现货优先

1. 现货侧按实际执行数量提交市价买单。
2. 等待该市价单达到可靠终态并读取实际成交数量 `Q` 与成交均价 `P`；`open`（含零成交或部分成交）期间保持 `EXECUTING`，不创建第二腿。
3. 如果 `Q` 为零，不提交合约订单，策略进入“执行失败”。
4. 如果 `Q` 大于零，合约侧提交等价标的数量 `Q`、限价 `P` 的 GTC 开空单。
5. GTC 单部分成交时继续保留剩余数量，直至完全成交或发生外部取消、交易所取消或拒单。

若第一腿市价单在 `closed` 或 `canceled` 终态只部分成交，以可靠的实际成交数量 `Q` 作为最终对冲目标，不继续追求用户最初输入的数量。

### 7.3 并发

1. 同时向现货侧提交市价买单，向合约侧提交市价开空单。
2. 等待两笔市价单都达到可靠终态，分别取得现货实际成交标的数量和合约实际做空标的数量。任一订单仍为 `open` 时保持 `EXECUTING`，不创建差额 GTC，也不判定最终敞口。
3. 如果两边成交数量相等且大于零，策略进入“对冲完成”。即使两边都小于用户输入数量，也不继续追量。
4. 如果两边成交数量都为零，策略进入“执行失败”。
5. 如果两边数量不等，在成交较少的一边补挂差额 GTC 限价单：
   - 现货不足：按合约订单的实际成交均价补挂现货买单。
   - 合约空仓不足：按现货订单的实际成交均价补挂合约开空单。
6. 差额 GTC 单部分成交时继续保留剩余数量，直至两边数量相等或订单发生外部取消、交易所取消或拒单。

并发模式的最终对冲目标是两笔市价单中较大的实际成交标的数量，而不是用户最初输入的数量。

## 8. 状态模型

策略只使用以下状态：

- `PENDING_CONFIRMATION`（待确认）：已完成预检，尚未提交订单。
- `EXECUTING`（执行中）：正在提交市价订单或等待市价订单终态。
- `WAITING_HEDGE`（等待对冲）：已有单边或不等量成交，GTC 单正在等待成交。
- `HEDGED`（对冲完成）：本策略两边实际成交的标的币数量相等且大于零。
- `HEDGE_INCOMPLETE`（对冲未完成）：存在裸露数量，但 GTC 单被拒绝、被交易所或外部操作取消，或缺少生成 GTC 单所需的可靠成交数据。
- `FAILED`（执行失败）：没有任何订单成交，因此没有产生本策略持仓。

`HEDGED`、`HEDGE_INCOMPLETE` 和 `FAILED` 是本期终态。系统不从这些状态自动重新下单。

## 9. 组件边界

### 9.1 交易所适配器

封装 CCXT，统一：

- 现货与永续市场加载。
- 账户设置和余额读取。
- 市价单、GTC 限价单和订单查询。
- 双向持仓模式的开空参数，以及用于预检拒绝单向模式的账户状态读取。
- 合约张数、标的数量、数量精度和价格精度转换。

适配器只负责单个交易所操作，不包含跨交易所策略状态。第一版在统一接口后分别提供 Bitget 与 OKX 参数配置，处理各自的客户订单 ID、GTC、持仓方向和订单查询差异；未配置的交易所必须在预检阶段被拒绝。

### 9.2 开仓预检器

验证市场、权限、余额、保证金、账户设置和共同可执行数量，并生成用户确认快照。它不提交订单。

### 9.3 对冲执行协调器

根据显式执行模式编排订单，计算第一腿实际成交量、第二腿或并发差额，并驱动策略状态转换。对同一策略只能有一个执行协调器实例进入下单临界区。

### 9.4 策略记录与订单监控器

使用 SQLite 保存策略、订单和状态变化。监控器按交易所订单 ID 查询未完成订单，更新累计成交，并在服务重启后恢复 `EXECUTING` 和 `WAITING_HEDGE` 策略。对 `EXECUTING`，监控器本身不创建订单；只有在顺序模式第一张市价单或并发模式两张市价单构成完整、可靠终态且尚无 GTC 时，才在释放策略操作所有权后调用同一个协调器继续派生 GTC。零个/单个并发意图及 `planned/open/unknown` 不触发该 continuation。

## 10. 持久化与幂等

策略记录至少包含：

- 策略 ID、创建时间和更新时间。
- 两家交易所、统一交易标的和交易所市场标识。
- 用户输入数量、实际执行数量和执行模式。
- 合约账户设置快照。
- 当前状态及最后异常。

订单记录至少包含：

- 所属策略、订单角色和交易所。
- 客户端订单 ID 与交易所订单 ID。
- 市场、订单类型、方向、价格和数量。
- 累计成交数量、成交均价、剩余数量和订单状态。
- 创建时间、更新时间和最后查询时间。

每个策略订单角色具有唯一约束。客户端订单 ID 根据“策略 ID + 订单角色”确定性生成 32 位小写字母数字摘要，以满足 OKX 长度和字符限制，并与订单角色一同持久化。提交订单前先保存该客户端订单 ID；发生超时后先按客户端订单 ID 或交易所订单 ID 查询，不直接重复提交，以避免网络超时造成重复下单。

策略状态变化和订单成交变化必须在 SQLite 事务中持久化。

## 11. 异常与恢复

- 市价单可靠终态零成交或下单明确失败：不提交后续 GTC；没有敞口时进入 `FAILED`。
- 市价单可靠终态为 `canceled` 且有可靠正成交量和实际均价：按真实部分成交继续对冲。
- 第一腿已有成交但无法取得可靠成交均价：进入 `HEDGE_INCOMPLETE`，不猜测价格。
- GTC 部分成交：保持 `WAITING_HEDGE`，继续监控剩余数量。
- GTC 被拒绝、外部撤销或交易所取消：保留已有持仓，进入 `HEDGE_INCOMPLETE`。
- 订单提交结果超时或未知：保留 `EXECUTING` 和已持久化意图，先按确定性 client order ID 查询确认订单是否存在，不直接重下。
- 创建结果已返回但本地快照附加暂时失败，或 API 查询暂时失败：保留 `EXECUTING`、当前订单意图和订单 ID；连接或存储恢复后查询并附加同一外部订单。
- 服务重启：扫描 `EXECUTING` 和 `WAITING_HEDGE` 策略，与交易所订单状态对账；完整已提交市场单拓扑达到可靠终态后自动由协调器继续，否则保持只查询恢复。
- 系统不自动平仓、撤单、改价或重新提交已被取消、拒绝的 GTC 单。

每次下单响应、订单状态和成交变化均记录交易所、订单 ID、方向、数量、均价、状态与时间。日志不得输出 API 密钥或签名材料。

## 12. 安全约束

- 交易所 API 密钥不得以明文写入 SQLite、源码或日志。
- API 密钥应只具备读取和交易权限，不启用提现权限。
- 下单接口必须防止同一策略被重复确认或并发执行。
- 所有用户确认信息和交易所响应使用统一策略 ID 关联，便于审计。

## 13. 测试范围

### 13.1 单元测试

- 合约乘数与标的币数量换算。
- 共同可执行数量计算。
- 数量和价格精度规范化。
- 三种执行模式的状态转换。
- 并发模式差额与补单方向计算。
- 原生浮点数未进入订单计算路径。

### 13.2 协调器测试

使用可编程的模拟交易所覆盖：

- 合约优先、现货优先和并发的完整成交。
- 第一腿市价单部分成交。
- 市价单 `open/0 -> open/partial -> closed/positive`、并发异步终态和重启恢复期间不提前补单或终态化；完整可靠终态后自动且只创建一张所需 GTC，重复监控轮不重复创建。
- 单个并发意图、`planned/open/unknown` 和其他不完整拓扑只查询、附加和保留 `EXECUTING`，监控器不创建缺失市场意图。
- CCXT 统一 `average=0` 从可靠 cost/trades 回退，无可靠证据时保持缺失；负数和非数字仍拒绝。
- `canceled` 市价单的可靠正成交，以及 `closed/canceled` 并发组合。
- 并发两边成交数量相等但小于输入数量。
- 并发成交数量不一致后的差额 GTC 补挂。
- GTC 多次部分成交后完全成交。
- GTC 被拒绝、外部撤销和交易所取消。
- 下单超时但交易所实际已创建订单。
- 下单副作用未知后首次查询失败、以及创建成功后本地快照附加失败，恢复时不重复创建。
- API 查询中断后恢复。
- 服务重启后的订单对账和监控恢复。
- 重复确认和并发执行不会产生重复订单。

### 13.3 集成测试

通过 CCXT 沙盒或受控模拟服务验证两家交易所之间的端到端流程。集成测试不得使用真实资金；正式接入单个交易所前还需验证该交易所的市场标识、持仓模式参数、GTC 支持和订单查询语义。

## 14. 验收标准

满足以下条件视为本期开仓策略实现完成：

1. 用户可显式选择三种执行模式之一，并在确认前看到完整参数和风险提示。
2. 现货和合约交易所只能从 Bitget 与 OKX 中分别选择，且不能选择同一家交易所。
3. 两种顺序模式按第一腿实际成交数量和均价创建第二腿 GTC 单。
4. 并发模式能识别实际成交差额并在较少一边创建正确的 GTC 差额单。
5. GTC 部分成交期间保持监控，不自动撤单、改价、重下或回滚。
6. 两边本策略实际成交标的数量相等时进入 `HEDGED`。
7. 交易所取消或拒绝 GTC 单时保留已有持仓并进入 `HEDGE_INCOMPLETE`。
8. 服务重启后能够恢复未完成策略的订单监控。
9. 重复确认、网络超时或并发执行不会产生重复订单。
10. 单向持仓账户在预检持久化和下单前被拒绝；只为双向持仓构造开空参数。
11. 功能清单明确把卖出现货并平掉合约空单列为后续事项。
