# 对冲完全对账原则设计

日期：2026-09-05

状态：已批准

## 1. 目标

在 `docs/standards/code-rules.md` 增加一条硬约束：对账是对冲任务的重中之重。所有会推进对冲状态的路径，在任务最终完成或结束前，必须做完完全对账。对账未完成时，不得宣称对冲完成，也不得结束任务。

本次只落原则，不改协调器、订单监控或恢复实现。后续设计、实现和评审必须遵守本原则。

## 2. 范围

### 2.1 本次改动

- 只修改 `docs/standards/code-rules.md`，新增第 4 条。
- 不修改 `src/strategy/hedge-coordinator.ts`、`src/strategy/order-monitor.ts` 或其他实现、测试、操作文档。

### 2.2 原则适用路径

原则约束所有会推进对冲状态的路径：

- 协调器执行与续跑
- 订单监控
- 重启恢复

原则不约束只读状态查询。查询不得被理解成必须向交易所对账，也不得靠查询去完成对冲。

### 2.3 非目标

- 不在本次补齐现有实现里可能跳过的对账路径。
- 不改策略状态机、订单角色或残差计算公式。
- 不把只读 HTTP/UI 状态查询改成对账入口。

## 3. 完全对账

进入 `HEDGED`、`FAILED`、`HEDGE_INCOMPLETE`，或决定补 GTC 之前，必须同时满足：

1. 本地策略状态、本地订单、交易所快照三者一致，至少覆盖角色、数量、状态。
2. 已核对两腿成交量，并对残差给出唯一解释：已对冲、需补 GTC、或明确失败。

`EXECUTING` 且对账尚未完成时，任务可以继续等待；这不算最终完成或结束。`WAITING_HEDGE` 只表示市场腿对账后已决定并挂出 GTC，对冲任务本身尚未最终完成；GTC 成交后仍须再做完全对账，才能进入终态。

对账未完成包括：任一已持久化订单未按 client order ID 查回并落库、三方字段不一致、两腿成交量未核对、残差缺少唯一解释。此时不得转入上述终态，也不得宣称对冲完成。

## 4. 写入正文

第 4 条必须按以下正文写入，不得改语义：

```
4. **对冲必须完全对账**：对账是重中之重。凡会推进对冲状态的路径（协调器执行/续跑、订单监控、重启恢复），在进入 `HEDGED`、`FAILED`、`HEDGE_INCOMPLETE` 或决定补 GTC 之前，必须完成完全对账：本地策略状态、本地订单与交易所快照在角色、数量、状态上一致，并核对两腿成交量、对残差给出唯一解释（已对冲 / 需补 GTC / 明确失败）。不得在对账未完成时宣称对冲完成或结束任务。

   > 示例：并发开仓现货成交 `1`、合约成交 `0.6` 时，必须先对账再对合约补 `0.4` 的 GTC；不得直接标为 `HEDGED`，也不得在未查回两腿订单时标为 `FAILED`。
```

现有第 1 至 3 条保持不变。

## 5. 对后续工作的约束

任何后续对冲设计、实现或评审，若会推进对冲状态，都必须先证明终态或补 GTC 前存在完全对账。缺少对账的终态、跳过查回的失败、或未解释残差的 `HEDGED`，都视为违反本原则。

本次变更本身没有实现测试。落实本原则的后续实现必须用测试锁住：对账未完成不能进入终态，残差必须落到已对冲、需补 GTC 或明确失败之一。
